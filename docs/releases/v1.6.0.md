# v1.6.0 — Ręczne wdrażanie przez GitHub Actions

## English

The public site can now be updated from a single manual GitHub Actions run. The owner starts **Deploy public site** for `main` and types `deploy`. The workflow builds the commit only after Checks have passed for it, uploads the image over SSH with a pinned host key and runs a root-owned server script through one narrow sudo rule. Learner-facing behaviour is unchanged.

- The server script refuses a Compose file that differs from the server copy, insufficient disk (8 GiB) or memory (768 MiB `MemAvailable` for updates), a wrong checksum, an archive that would tag any other image and a mismatched revision label.
- Before switching the image it requires a fresh verified database backup. It changes only `SITE_IMAGE` atomically, keeps `.env.before-<sha>`, retains the release archive and records each deployment in `deployments.log`.
- If initialization fails, the previous image stays selected and the running API is untouched. If the new API is unhealthy, no automatic rollback happens: the script prints the rollback command, because schema compatibility must be checked first. Migrations are never reversed, and images, archives, volumes and backups are never deleted.
- The workflow tolerates private keys copied with broken line breaks and limits packet size only on the runner's route to the server. This works around large packets being lost between the hosted runner and the VPS.
- Initialization still disables AI on every deployment; re-enable it deliberately in `/admin`.

One-time server setup, GitHub secrets and rollback are described in `docs/site-deployment.md`. The server copy of `deploy.sh` is installed and updated manually.

The workflow deployed `aeef8de` to the public site successfully. Observed CI results are recorded in the published GitHub Release after verification.

## Polski

Publiczny serwis można teraz zaktualizować jednym ręcznym uruchomieniem GitHub Actions. Właściciel uruchamia **Deploy public site** dla `main` i wpisuje `deploy`. Workflow buduje commit dopiero wtedy, gdy przeszedł on Checks, przesyła obraz przez SSH ze sprawdzonym kluczem hosta i uruchamia skrypt serwera należący do roota przez jedną wąską regułę sudo. Działanie serwisu dla uczniów się nie zmienia.

- Skrypt serwera odmawia, gdy plik Compose różni się od kopii na serwerze, brakuje miejsca na dysku (8 GiB) lub pamięci (768 MiB `MemAvailable` przy aktualizacji), suma kontrolna się nie zgadza, archiwum oznaczałoby inny obraz albo etykieta wersji jest błędna.
- Przed zmianą obrazu wymaga nowej, sprawdzonej kopii bazy. Atomowo zmienia tylko `SITE_IMAGE`, zachowuje `.env.before-<sha>` i archiwum wydania oraz zapisuje każde wdrożenie w `deployments.log`.
- Gdy inicjalizacja się nie powiedzie, pozostaje poprzedni obraz, a działające API nie jest ruszane. Gdy nowe API nie jest zdrowe, skrypt nie cofa zmian automatycznie, tylko wypisuje polecenie powrotu, bo najpierw trzeba sprawdzić zgodność schematu. Migracje nigdy nie są cofane, a obrazy, archiwa, wolumeny i kopie zapasowe nie są usuwane.
- Workflow akceptuje klucz prywatny skopiowany z uszkodzonymi podziałami wierszy i ogranicza rozmiar pakietów tylko na trasie z maszyny GitHub do serwera. Omija to utratę dużych pakietów między maszyną GitHub a VPS.
- Inicjalizacja nadal wyłącza AI przy każdym wdrożeniu; włącz je świadomie w `/admin`.

Jednorazowa konfiguracja serwera, sekrety GitHub i powrót do poprzedniej wersji są opisane w `docs/site-deployment.md`. Kopię `deploy.sh` na serwerze instaluje się i aktualizuje ręcznie.

Workflow pomyślnie wdrożył `aeef8de` na publiczną stronę. Wyniki CI zostaną zapisane w GitHub Release po weryfikacji.
